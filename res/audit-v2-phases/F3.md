## Behavior decisions

- **Base reveal count is one; relics fold on top.** `run_select_node`'s archive
  case starts `reveal_count = 1`, fires the new run-side
  `QUERY_ARCHIVE_REVEAL_COUNT` over held relics through `run_fire_relics`, then
  reveals up to that many still-hidden recipes. The engine no longer names
  `RELIC_MASTERS_NOTES` in dispatch; the only remaining occurrence in `run.c`
  (line 267) is the archive node's relic-choice **content data**, not a branch.
- **Master's Notes owns its `+1` as an effect.** `RELIC_MASTERS_NOTES` gains an
  `.effects` entry `{ eff_masters_notes, QUERY_ARCHIVE_REVEAL_COUNT }` that does
  `*(int*) x += 1`. Future reveal-count modifiers compose on the same fold.
- **Deterministic registry order (documented).** The archive's designated recipe
  (`node->content`) reveals first when still hidden; remaining reveals pull the
  next still-hidden recipe results in `PieceID` registry order
  (`battle_is_recipe_result(id) && !pieces[id]`). Identical to prior behavior for
  count 1 and count 2 on the normal (content-hidden) path.
- **Still-hidden filtering (minor behavior refinement).** The old code
  unconditionally re-logged `node->content` even if already unlocked. The new
  fold only counts/reveals still-hidden recipes, matching the plan's "up to final
  count of still-hidden recipes" wording. Normal play (content not yet owned) is
  unchanged; only the degenerate already-owned-content case now fills from the
  pool instead of re-logging a known recipe.
- **Exhaustion is safe.** The fill loop is bounded by `PIECE_COUNT` and stops
  when no still-hidden recipe remains, so a requested count above the remaining
  pool reveals fewer without error.
- **No new save/load state.** Revealed recipes persist through the existing
  `run->pieces[]` bit string; F3 adds no serializer fields.
